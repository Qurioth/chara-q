# ADR 0006: 認証（招待コードでの登録、Vercel 経由の中継、DB セッション）

- ステータス: 採用
- 日付: 2026-10-30

## 背景

ADR 0001 では「Go が JWT を発行し、Next.js はそれを渡すだけ」という大枠だけを決め、
ログイン方法とトークンの保存場所は未決定にしていた。

前提は次のとおり。

- 利用者は小さなコミュニティで、管理者がいる（ADR 0005）。
- メールアドレスなどの個人情報は保持したくない。外部の認証サービスにも頼りたくない。
- 独自ドメインは使わず、web は `*.vercel.app`、api は Cloud Run の `*.run.app` で公開する。
  - どちらも Public Suffix List に載っているため、web と api は別サイトとして扱われる。
  - そのため、api が直接発行する Cookie はサードパーティ Cookie になり、Safari と Firefox では
    既定でブロックされる。

## 決定

### 登録とログイン

- **ユーザー登録には、ログイン ID・パスワード・管理者が発行した招待コードの 3 つを使う。**
  メールアドレスは持たない。
- **表示名はログイン ID とは別に持ち、後から変えられる。**
  - ログイン ID は他の人に見せない。表示名は公開する。
- **パスワードは Argon2id でハッシュにして保存する。**
- **ログインの失敗回数は Postgres に記録し、続けて失敗したら一定時間ロックする。**
  Cloud Run はインスタンスが複数になりうるため、メモリには持たない。
- **招待コードは推測できない長さのランダムな値にし、DB にはハッシュだけを保存する。**
  1 回だけ使え、有効期限を持つ。
- **パスワードを忘れた場合は、管理者がそのユーザー専用の再設定コードを発行する。**
  メールを持たないため、自分では再設定できない。再設定コードも招待コードと同じく、
  1 回だけ使えて有効期限がある。
- **最初の管理者ユーザーは Taskfile のコマンドで作る。** 最初は招待コードがないため。

### 通信経路とログイン状態

- **ブラウザは web（`*.vercel.app`）だけと通信する。**
  - Next.js の `rewrites` で、`/graphql` を Cloud Run の api に中継する。
  - 中継先の URL はサーバー側の環境変数に置き、`NEXT_PUBLIC_` にはしない。
- **ログイン状態は、DB で管理するセッションで持つ。JWT は使わない。**
  - Cookie にはランダムなセッション ID だけを入れる。DB にはそのハッシュを保存する。
  - Cookie には `HttpOnly`・`Secure`・`SameSite=Lax` を付け、`Domain` は付けない。
  - 次のときは、そのユーザーのセッションを DB から削除する。
    - ログアウトしたとき
    - パスワードを変えたとき
    - 管理者がユーザーを無効にしたとき
- **CSRF への対策として、ミューテーションは `POST` かつ `Content-Type: application/json` だけで
  受け付ける。**

## 後続の Spec で決めること

認証の Spec の `/speckit-clarify` で決める。

- ログイン ID に使える文字と長さ、パスワードの最小の長さ
- ロックするまでの失敗回数とロックの時間、招待コードと再設定コードの有効期限、
  セッションの有効期限
- 管理者の操作（招待コードの発行、ユーザーの無効化、所有者の移動）を、Taskfile の
  コマンドだけにするか、管理画面も作るか
- 招待コードに既存シートを紐づけ、登録したときに所有者を自動で移すか
  （ADR 0005 の「DB 操作で所有者を移す」を置き換える案）
- Server Components から api を呼ぶときに、Cookie をどう渡すか

認証の Spec の最初に、Vercel の `rewrites` を通しても `Set-Cookie` がブラウザに届き、
Cookie が api まで送られることを確かめる。

## 検討した代案

- **Discord・Google などの外部ログイン（OAuth）**: パスワードを保存しなくて済む。
  ただし外部サービスへの登録が必要で、利用者のアカウント情報を外部に頼ることになる。
- **トークンを JavaScript から読める場所に置き、`Authorization` ヘッダーで送る**: 中継はいらない。
  ただし XSS でトークンを盗まれる危険がある。
- **独自ドメインを使い、web と api を同じドメインの下に置く**: ドメイン代がかかる。
  さらに、Cloud Run に独自ドメインを付ける機能はリージョンによって使えず、ロードバランサーを
  使うと月額費用がかかる。
- **JWT**: ADR 0001 の当初案。DB を見ずに検証できるが、発行したトークンは期限まで取り消せない。
  ユーザーの無効化やパスワード変更をすぐに反映させたいため、採らない。

## 結果

- メールアドレスなどの個人情報を持たずに済む。登録できるのは、管理者が招待した人だけになる。
- 管理者の作業が増える。招待コードと再設定コードの発行が、管理者の作業になる。
- web と api が同じオリジンに見えるため、本番では CORS の設定がいらなくなる。
  - `CORS_ALLOWED_ORIGINS` と GitHub 変数 `CLOUD_RUN_CORS_ALLOWED_ORIGINS` を外すかは、
    認証の Spec で決める。
- 今の骨格の urql は `NEXT_PUBLIC_API_URL` で api に直接つないでいる。これは認証の Spec で、
  相対パスの `/graphql` に変える。
- api へのリクエストは Vercel を経由するため、通信が 1 段増える。
- Cloud Run の URL は公開されたまま残る。ただし、セッションの Cookie は `vercel.app` 側にしか
  送られないため、Cloud Run の URL に直接アクセスしてもログイン状態は使えない。
