# Feature Specification: 認証（招待コードでの登録、ログイン・ログアウト）

**Feature Branch**: `002-auth`

**Created**: 2026-10-31

**Status**: Draft

**Input**: User description: "認証: 管理者が発行した招待コードでユーザー登録し、ログイン・ログアウトできるようにする。ADR 0006 の決定に従う。（利用者ができること: 招待コード・ログイン ID・パスワード・表示名での登録、ログイン・ログアウトとヘッダーへのログイン状態の表示、表示名とパスワードの変更、再設定コードでのパスワードの再設定。管理者ができること: 招待コードの発行、再設定コードの発行、ユーザーの無効化、最初の管理者ユーザーを Taskfile のコマンドで作る。守ること: web 経由の中継、DB で管理するセッション、平文で保存しない、ログインの失敗でのロック、セッションの削除、ミューテーションの受け付け条件、中継を通した Cookie の確認。含めないもの: キャラクターシートの作成・更新と所有者の確認、本番環境の構築とデプロイ。clarify で決めること: ADR 0006 の「後続の Spec で決めること」と CORS の設定の扱い）"

## Clarifications

### Session 2026-10-31

- Q: ログイン ID に使える文字と長さ、パスワードの最小の長さを、どの規則にするか？ → A: ログイン ID は半角英数字・`_`・`-` の 3〜32 文字（大文字と小文字は区別しない）。パスワードは 8〜128 文字で、文字の種類は問わない。表示名は 1〜32 文字。
- Q: ロックするまでの失敗回数とロックの時間、招待コード・再設定コード・セッションの有効期限を、どの組み合わせにするか？ → A: 5 回続けて失敗したら 15 分ロックする。招待コードは 7 日、再設定コードは 24 時間。セッションは最後に使ってから 30 日で、使うたびに延びる。
- Q: 管理者の操作を、Taskfile のコマンドだけで行うか、web に管理画面も作るか？ → A: 招待コードの発行だけを web の管理画面（管理者だけが使える）で行う。最初の管理者の作成、再設定コードの発行、ユーザーの一覧・無効化・有効化は Taskfile のコマンドで行う。
- Q: 招待コードに既存のシートを紐づけ、登録したときにシートの所有者を自動で移すか？ → A: この機能では何も用意しない。紐づけるかどうかは、データ移行の機能でもう一度決める。
- Q: Server Components から api を呼ぶときに Cookie をどう渡し、CORS の許可（`CORS_ALLOWED_ORIGINS` と `CLOUD_RUN_CORS_ALLOWED_ORIGINS`）を外すか？ → A: Server Components は、受け取った Cookie のうちセッションの Cookie だけを、サーバー側の環境変数にある api の URL へ直接付けて送る。CORS の許可は、ローカル・CI・本番のすべてで外す。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理者を作り、ログイン・ログアウトする (Priority: P1)

開発者（運用者）は、コマンドで最初の管理者ユーザーを作る。管理者はログイン画面でログイン ID と
パスワードを入力してログインし、ヘッダーの右端に自分の表示名とログアウトの操作が表示される。
ログアウトすると、ヘッダーはログインの操作に戻る。ログインしていない訪問者には、ヘッダーに
ログインの操作が表示される。

**Why this priority**: 招待コードの発行も、後の機能のシートの作成・更新も、ログインした
ユーザーがいることを前提にする。最初は招待コードがないため、コマンドで管理者を作れないと
誰もログインできない。また、ADR 0006 の中継の経路でログイン状態が保てることを、この
ストーリーで最初に確かめる。

**Independent Test**: 空の DB でコマンドを実行して管理者を作り、ログイン・再読み込み・
ログアウトを行う。Chrome・Safari・Firefox の既定の設定で、ログイン状態が保たれることを確かめる。

**Acceptance Scenarios**:

1. **Given** ユーザーが 1 人もいない, **When** 開発者がコマンドでログイン ID・パスワード・表示名を指定して管理者を作る, **Then** 管理者ユーザーができ、そのログイン ID とパスワードでログインできる
2. **Given** ログインしていない, **When** 任意の画面を開く, **Then** ヘッダーの右端の操作の領域にログインへの操作が表示される
3. **Given** 登録済みのユーザー, **When** 正しいログイン ID とパスワードでログインする, **Then** ログイン前に見ていた画面（ログイン画面を直接開いた場合はトップページ）に戻り、ヘッダーに自分の表示名とログアウトの操作が表示される
4. **Given** ログインしている, **When** 再読み込みする・ブラウザのタブを閉じて開き直す, **Then** ログインしたままで、最初の描画から表示名が表示される（ログインしていない表示が一瞬出ることはない）
5. **Given** ログインしている, **When** ログアウトする, **Then** ログインしていない表示に戻り、ログアウト前に使っていたログイン状態は、同じブラウザからも他の手段からも二度と使えない
6. **Given** 誤ったパスワード・存在しないログイン ID, **When** ログインする, **Then** どちらの場合も同じ文言で失敗が表示され、どちらが誤っているかはわからない
7. **Given** Safari・Firefox・Chrome（いずれも既定の設定）, **When** ログインして別の画面に移動する, **Then** どのブラウザでもログイン状態が保たれる

### User Story 2 - 招待コードで登録する (Priority: P1)

管理者はログインして招待コードの発行画面で招待コードを発行し、アプリの外（チャットなど）で
招待する人に渡す。招待された人は
登録画面で、招待コード・ログイン ID・パスワード・表示名を入力して登録する。メールアドレスは
入力しない。登録が終わると、そのままログインした状態になる。

**Why this priority**: 管理者以外の利用者がアプリを使い始める唯一の入口であり、登録できる
人を管理者が招待した人だけに限るという ADR 0006 の決定の中心になる。

**Independent Test**: 管理者が招待コードを発行し、別のブラウザでそのコードを使って登録する。
同じコードでの 2 回目の登録と、期限切れのコードでの登録が拒否されることを確かめる。

**Acceptance Scenarios**:

1. **Given** 管理者としてログインしている, **When** 招待コードの発行画面で招待コードを発行する, **Then** 推測できないランダムな招待コードと、その有効期限（発行から 7 日）が管理者にだけ表示される。招待コードの値は発行したときにしか表示されない
2. **Given** 管理者でないユーザー・ログインしていない訪問者, **When** 招待コードの発行画面を開く・発行の操作を API に直接送る, **Then** 画面は表示されず（ログインしていなければログイン画面に移動する）、招待コードは発行されない。ヘッダーにも発行画面への入口は表示されない
3. **Given** 未使用で期限内の招待コード, **When** 招待コード・ログイン ID・パスワード・表示名を入力して登録する, **Then** ユーザーができてログインした状態になり、ヘッダーに表示名が表示される
4. **Given** 一度使った招待コード, **When** 別の人がそのコードで登録する, **Then** 登録できず、招待コードが使えないことが表示される
5. **Given** 期限が切れた招待コード・存在しない招待コード, **When** 登録する, **Then** 登録できず、使用済みの場合と同じ文言で、招待コードが使えないことが表示される
6. **Given** 既に使われているログイン ID（大文字と小文字の違いだけのものを含む）, **When** そのログイン ID で登録する, **Then** 登録できず、ログイン ID が使えないことが表示される。招待コードは未使用のまま残る
7. **Given** 規則に合わないログイン ID・短すぎるパスワード・空の表示名, **When** 登録する, **Then** 登録できず、どの項目をどう直せばよいかが項目の近くに表示される。招待コードは未使用のまま残る
8. **Given** 登録画面, **When** 項目を見る, **Then** メールアドレスなど、招待コード・ログイン ID・パスワード・表示名以外の個人情報を求める項目はない

### User Story 3 - 続けて失敗したログインをロックする (Priority: P2)

同じログイン ID でログインに続けて失敗すると、そのログイン ID は 15 分ログインできなくなる。
ロックの間は、正しいパスワードを入力してもログインできない。時間が過ぎると再びログインできる。

**Why this priority**: パスワードの総当たりから利用者を守る。ログインそのもの（P1）があれば
後から追加できるため P2 とする。

**Independent Test**: 誤ったパスワードで5 回続けて失敗し、その後に正しい
パスワードでもログインできないこと、15 分が過ぎるとログインできることを確かめる。

**Acceptance Scenarios**:

1. **Given** 登録済みのユーザー, **When** 誤ったパスワードで5 回続けてログインに失敗する, **Then** そのログイン ID はロックされ、ロック中であること（いつまでかの目安を含む）が表示される
2. **Given** ロック中のログイン ID, **When** 正しいパスワードでログインする, **Then** ログインできない
3. **Given** ロック中のログイン ID, **When** ロックから 15 分が過ぎてから正しいパスワードでログインする, **Then** ログインでき、失敗の回数は 0 に戻る
4. **Given** 4 回以下の失敗のあと, **When** 正しいパスワードでログインする, **Then** ログインでき、失敗の回数は 0 に戻る
5. **Given** 存在しないログイン ID, **When** 5 回続けてログインに失敗する, **Then** 存在するログイン ID と同じようにロックの表示になり、そのログイン ID が存在しないことはわからない
6. **Given** あるログイン ID がロックされている, **When** 別のユーザーがログインする, **Then** 別のユーザーのログインには影響しない

### User Story 4 - 表示名とパスワードを変える (Priority: P2)

ログインしたユーザーは、自分のアカウントの設定画面で、表示名とパスワードを変えられる。
表示名は他の人にも公開され、ログイン ID は自分にだけ表示される。パスワードを変えると、
ほかの端末のログイン状態はすべて切れる。

**Why this priority**: 登録とログイン（P1）がなくても困らないが、表示名は公開されるため、
登録後に直せる手段が必要になる。パスワードの変更は、漏れた疑いがあるときの自衛の手段になる。

**Independent Test**: 2 つのブラウザで同じユーザーとしてログインし、片方で表示名とパスワードを
変える。表示名がヘッダーに反映されること、もう片方のブラウザがログアウトした状態になることを
確かめる。

**Acceptance Scenarios**:

1. **Given** ログインしている, **When** アカウントの設定画面を開く, **Then** 自分のログイン ID と表示名が表示される。ログイン ID は変えられない
2. **Given** ログインしている, **When** 表示名を変えて保存する, **Then** ヘッダーの表示名がすぐに新しい表示名になる
3. **Given** ログインしている, **When** 現在のパスワードと新しいパスワードを入力して保存する, **Then** パスワードが変わり、この画面のブラウザはログインしたまま、ほかのブラウザ・端末のログイン状態はすべて切れる
4. **Given** ログインしている, **When** 誤った現在のパスワードでパスワードを変えようとする, **Then** 変更できず、現在のパスワードが違うことが表示される
5. **Given** 別のユーザー・ログインしていない訪問者, **When** アプリのどの画面や応答を見ても, **Then** 他のユーザーのログイン ID は見えない（表示名だけが見える）
6. **Given** ログインしていない, **When** アカウントの設定画面を開く, **Then** ログイン画面に移動し、ログインするとアカウントの設定画面に戻る

---

### User Story 5 - 再設定コードでパスワードを再設定する (Priority: P2)

パスワードを忘れたユーザーは、アプリの外で管理者に連絡する。管理者はそのユーザー専用の
再設定コードを発行して渡す。ユーザーは再設定画面で、ログイン ID・再設定コード・新しい
パスワードを入力し、パスワードを設定し直す。

**Why this priority**: メールアドレスを持たないため、パスワードを忘れた利用者が戻ってこられる
唯一の手段になる。ただし、登録とログイン（P1）が先に必要で、頻度も低いため P2 とする。

**Independent Test**: 管理者が再設定コードを発行し、ユーザーがそのコードで新しいパスワードを
設定する。古いパスワードでログインできないこと、同じコードを 2 回使えないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 管理者, **When** ログイン ID を指定して再設定コードを発行する, **Then** そのユーザー専用の推測できないランダムな再設定コードと、その有効期限が管理者にだけ表示される。値は発行したときにしか表示されない
2. **Given** 未使用で期限内の再設定コード, **When** ユーザーがログイン ID・再設定コード・新しいパスワードを入力する, **Then** パスワードが変わり、そのユーザーの既存のログイン状態はすべて切れ、新しいパスワードでログインできる。古いパスワードではログインできない
3. **Given** 一度使った・期限が切れた・別のユーザー用の再設定コード, **When** 再設定する, **Then** 再設定できず、どの場合も同じ文言で、再設定コードが使えないことが表示される
4. **Given** ログインがロックされているユーザー, **When** 再設定コードでパスワードを再設定する, **Then** ロックが解け、新しいパスワードですぐにログインできる
5. **Given** 未使用の再設定コードがあるユーザー, **When** 管理者が同じユーザーに新しい再設定コードを発行する, **Then** 前の再設定コードは使えなくなる

---

### User Story 6 - 管理者がユーザーを無効にする (Priority: P2)

管理者は、問題のあるユーザーや、コミュニティを離れたユーザーを無効にする。無効にした
ユーザーのログイン状態はすぐに切れ、以後はログインできない。

**Why this priority**: 招待制のコミュニティを管理者が保つための手段。登録（P1）が始まる前に
用意しておくのが望ましいが、ユーザーが少ないうちは急がないため P2 とする。

**Independent Test**: ユーザーがログインしている状態で管理者がそのユーザーを無効にし、
ユーザーの次の操作がログインしていない扱いになること、再びログインできないことを確かめる。

**Acceptance Scenarios**:

1. **Given** ログインしているユーザー, **When** 管理者がそのユーザーを無効にする, **Then** そのユーザーのすべてのログイン状態が切れ、次の画面の表示や操作からログインしていない扱いになる
2. **Given** 無効にしたユーザー, **When** 正しいログイン ID とパスワードでログインする, **Then** ログインできず、誤ったパスワードの場合と同じ文言で失敗が表示される
3. **Given** 無効にしたユーザー, **When** 管理者が再設定コードを発行しようとする, **Then** 発行できず、ユーザーが無効であることが管理者に表示される
4. **Given** 無効にしたユーザー, **When** 管理者が有効に戻す, **Then** そのユーザーは元のパスワードで再びログインできる
5. **Given** 無効にしたユーザー, **When** 他の人がその表示名やログイン ID を見ようとする, **Then** ログイン ID は見えないまま、表示名の扱いは無効にする前と変わらない（後の機能で、そのユーザーが所有するシートの表示に使う）

---

### Edge Cases

- 同じ招待コードで、ほぼ同時に 2 人が登録したときは、1 人だけが登録でき、もう 1 人には
  招待コードが使えないことが表示される。同じ再設定コードを同時に使った場合も、1 回だけ成功する。
- 登録の途中で招待コードの期限が切れたとき（画面を開いたまま期限を過ぎて送信したなど）は、
  送信した時点で判定し、期限切れとして拒否する。
- ログインしたまま、セッションの有効期限が切れたときは、次の画面の表示や操作からログイン
  していない扱いになる。ログインが必要な操作だった場合は、ログイン画面に移動し、ログイン後に
  元の画面に戻る。
- ログイン状態の Cookie を手で書き換えた・偽造したときは、ログインしていない扱いになる。
  エラー画面にはしない。
- ログインの後の戻り先として、アプリの外の URL を指定されたときは、外には移動せず
  トップページに戻る。
- ログイン ID の前後の空白は取り除いて扱う。大文字と小文字は区別せず、同じログイン ID と
  みなす。表示名の前後の空白も取り除き、空白だけの表示名は空として扱う。
- 表示名に改行などの制御文字が含まれるときは、受け付けない。日本語・絵文字は受け付ける。
- 表示名は他のユーザーと同じでもよい。
- パスワードの前後の空白は取り除かず、入力したとおりに扱う。
- ログインしたまま別のブラウザでパスワードを変えた・管理者に無効にされたときは、元の
  ブラウザで次に画面を表示したときにログインしていない表示になる。
- 管理者を作るコマンドで、既に使われているログイン ID を指定したときは、失敗して既存の
  ユーザーは変わらない。2 人目以降の管理者もこのコマンドで作れる。
- api に直接（web を経由せずに）アクセスしても、ブラウザのログイン状態は使えない。
- ミューテーションを、POST 以外、または JSON 以外の形式で送られたときは、処理せずに拒否する。
- ローカル開発の環境（`http://localhost`）でも、本番と同じ Cookie の属性でログイン状態が
  保てる。

## Requirements *(mandatory)*

### Functional Requirements

#### 通信経路とログイン状態の保持（ADR 0006）

- **FR-001**: ブラウザは web とだけ通信しなければならない（MUST）。API へのリクエストは web が中継し、中継先の API の URL はブラウザに公開してはならない（MUST NOT）。ブラウザの API の接続先は、web と同じオリジンの相対パスにする（MUST）。
- **FR-002**: ログイン状態はサーバー側の DB で管理するセッションで持たなければならない（MUST）。ブラウザにはランダムなセッション ID だけを Cookie で渡し、ユーザーの情報や署名付きのトークン（JWT など）を入れてはならない（MUST NOT）。
- **FR-003**: セッションの Cookie は、JavaScript から読めず（HttpOnly）、安全な接続でだけ送られ（Secure）、他のサイトからのリクエストではページの移動のとき以外は送られない（SameSite=Lax）ものでなければならない（MUST）。Cookie のドメインは指定しない（MUST）。
- **FR-004**: この機能の実装の最初に、web の中継を通しても、API が設定した Cookie がブラウザに届き、ブラウザの Cookie が API まで届くことを確かめなければならない（MUST）。確かめられなかった場合は、以降の実装に進まずに方針を見直す。
- **FR-005**: API は、ミューテーションを POST かつ `Content-Type: application/json` のリクエストでだけ受け付けなければならない（MUST）。それ以外の形式のミューテーションは処理せずに拒否する。
- **FR-006**: サーバー側で描画する画面も、ブラウザのログイン状態に応じた内容を最初の描画から表示しなければならない（MUST）。サーバー側の描画のために web が API を呼ぶときは、ブラウザから受け取った Cookie のうちセッションの Cookie だけを付けて、サーバー側の環境変数にある API の URL へ直接送る（MUST）。ほかの Cookie を API に送ってはならない（MUST NOT）。

#### 保存してはならないもの

- **FR-007**: パスワードは Argon2id でハッシュにして保存し、平文や元に戻せる形で保存してはならない（MUST NOT）。
- **FR-008**: 招待コード・再設定コード・セッション ID は、元の値を復元できない形（ハッシュ）でだけ保存しなければならない（MUST）。
- **FR-009**: メールアドレスなど、ログイン ID・パスワード・表示名以外の個人情報を、登録やアカウントの設定で求めても保存してもならない（MUST NOT）。
- **FR-010**: パスワード・招待コード・再設定コード・セッション ID の値を、ログ（アクセスログ、エラーログを含む）に出してはならない（MUST NOT）。

#### 登録

- **FR-011**: 訪問者は、招待コード・ログイン ID・パスワード・表示名を入力して登録できなければならない（MUST）。登録に成功したら、そのままログインした状態にする（MUST）。
- **FR-012**: 招待コードは、未使用で有効期限内のときだけ使え、1 回使ったら使えなくしなければならない（MUST）。同時に使われても、成功するのは 1 回だけにする（MUST）。
- **FR-013**: 使えない招待コード（存在しない・使用済み・期限切れ）での登録は、どの理由でも同じ文言で拒否しなければならない（MUST）。
- **FR-014**: 登録が招待コード以外の理由（ログイン ID が使われている、入力の規則に合わないなど）で失敗したときは、招待コードを未使用のまま残さなければならない（MUST）。
- **FR-015**: ログイン ID は、ユーザーの間で一意でなければならない（MUST）。大文字と小文字の違いだけのログイン ID は同じものとみなす（MUST）。登録した後は変えられない。
- **FR-016**: 登録とアカウントの設定では、次の規則で入力を検証し、規則に合わない項目と直し方を項目の近くに表示しなければならない（MUST）。
  - ログイン ID: 半角英数字・`_`・`-` だけの 3〜32 文字。
  - パスワード: 8〜128 文字。文字の種類（英字・数字・記号の組み合わせ）は求めない。
  - 表示名: 前後の空白を除いて 1〜32 文字。

#### ログイン・ログアウト

- **FR-017**: ユーザーは、ログイン ID とパスワードでログインできなければならない（MUST）。
- **FR-018**: ログインの失敗は、ログイン ID が存在しない・パスワードが違う・ユーザーが無効、のどの場合も同じ文言で表示しなければならない（MUST）。
- **FR-019**: ログインに成功したら、新しいセッション ID を発行しなければならない（MUST）。ログイン前のセッション ID を使い続けてはならない（MUST NOT）。
- **FR-020**: ログインに成功したら、ログイン前に見ていた画面に戻さなければならない（MUST）。戻り先は同じアプリの中の画面だけとし、アプリの外の URL には移動させてはならない（MUST NOT）。
- **FR-021**: ユーザーはログアウトできなければならない（MUST）。ログアウトしたら、そのセッションを DB から削除し、ブラウザの Cookie も消さなければならない（MUST）。
- **FR-022**: セッションの有効期限は、最後に使ってから 30 日とし、使うたびに延ばさなければならない（MUST）。期限が切れたセッションはログインしていない扱いにする（MUST）。ログインからの上限は設けない。
- **FR-023**: 無効・期限切れ・存在しないセッション ID が送られたときは、エラーにせずログインしていない扱いにしなければならない（MUST）。

#### ヘッダーのログイン状態

- **FR-024**: ヘッダーの右端の操作の領域に、ログイン状態を表示しなければならない（MUST）。ログインしていないときはログインへの操作を、ログインしているときは自分の表示名とログアウトの操作を表示する。表示名からはアカウントの設定画面に移動できる（MUST）。
- **FR-025**: ログイン状態の表示は、テーマの切り替えと並べて、幅 360px の画面でも重ならず、横スクロールを発生させてはならない（MUST NOT）。長い表示名は省略して表示する。
- **FR-026**: ログイン画面から登録画面とパスワードの再設定画面に、登録画面からログイン画面に移動できなければならない（MUST）。

#### ログインの失敗とロック

- **FR-027**: ログインの失敗の回数は、ログイン ID ごとに DB に記録しなければならない（MUST）。サーバーのメモリにだけ持ってはならない（MUST NOT）。
- **FR-028**: 5 回続けてログインに失敗したログイン ID は、5 回目の失敗から 15 分ロックし、その間は正しいパスワードでもログインさせてはならない（MUST NOT）。ロック中のログインの試みは、失敗の回数にもロックの時間にも加えない。
- **FR-029**: ロック中であることは、ロックが解ける時刻の目安と一緒に表示しなければならない（MUST）。存在しないログイン ID も同じように失敗を数え、同じようにロックの表示にする（MUST）。
- **FR-030**: ログインに成功したとき、パスワードを再設定したときは、失敗の回数を 0 に戻し、ロックを解かなければならない（MUST）。

#### アカウントの設定

- **FR-031**: ログインしたユーザーは、アカウントの設定画面で、自分のログイン ID（変更不可）と表示名を確認し、表示名を変えられなければならない（MUST）。
- **FR-032**: ログインしたユーザーは、現在のパスワードと新しいパスワードを入力して、パスワードを変えられなければならない（MUST）。現在のパスワードが違うときは変更しない（MUST）。
- **FR-033**: パスワードを変えたら、そのユーザーのセッションをすべて削除しなければならない（MUST）。変更した画面のブラウザには新しいセッションを発行し、ログインしたままにする（MUST）。
- **FR-034**: ログイン ID は本人にだけ見せなければならない（MUST）。他のユーザーとログインしていない訪問者には、どの画面や API の応答でもログイン ID を返してはならない（MUST NOT）。表示名は公開してよい。
- **FR-035**: ログインしていないときにアカウントの設定画面を開いたら、ログイン画面に移動させ、ログイン後に戻さなければならない（MUST）。

#### パスワードの再設定

- **FR-036**: ユーザーは、ログイン ID・再設定コード・新しいパスワードを入力して、パスワードを再設定できなければならない（MUST）。
- **FR-037**: 再設定コードは、発行したユーザーにだけ、未使用で有効期限内のときだけ使え、1 回使ったら使えなくしなければならない（MUST）。同時に使われても、成功するのは 1 回だけにする（MUST）。
- **FR-038**: 使えない再設定コード（存在しない・使用済み・期限切れ・別のユーザー用）での再設定は、どの理由でも同じ文言で拒否しなければならない（MUST）。
- **FR-039**: パスワードを再設定したら、そのユーザーのセッションをすべて削除しなければならない（MUST）。
- **FR-040**: 再設定の画面での失敗も、ログインと同じように回数を数えてロックしなければならない（SHOULD）。再設定コードの総当たりを防ぐため。

#### 管理者の操作

招待コードの発行は web の管理画面で、それ以外の管理者の操作は Taskfile のコマンドで行う。
コマンドは、接続先の DB を受け取って直接操作する（web と API は経由しない）。

- **FR-041**: 開発者は、コマンドで管理者ユーザーを作れなければならない（MUST）。コマンドはログイン ID・パスワード・表示名を受け取り、パスワードをコマンドの履歴に残さない方法で受け取る（SHOULD）。
- **FR-042**: 管理者は、ログインして web の招待コードの発行画面で、招待コードを発行できなければならない（MUST）。招待コードは推測できない長さのランダムな値で、発行したときに一度だけ値と有効期限を画面に表示する（MUST）。有効期限は発行から 7 日とする（MUST）。
- **FR-043**: 管理者は、コマンドでログイン ID を指定して、そのユーザー専用の再設定コードを発行できなければならない（MUST）。値と有効期限は発行したときに一度だけ表示する（MUST）。有効期限は発行から 24 時間とする（MUST）。同じユーザーの未使用の再設定コードは、新しいコードの発行で使えなくする（MUST）。無効なユーザーには発行しない（MUST）。
- **FR-044**: 管理者は、コマンドでログイン ID を指定して、ユーザーを無効にできなければならない（MUST）。無効にしたら、そのユーザーのセッションをすべて削除し、以後のログインを拒否する（MUST）。無効にしたユーザーを有効に戻すこともできる（MUST）。
- **FR-045**: 管理者は、コマンドでユーザーの一覧（ログイン ID・表示名・管理者かどうか・有効か無効か）を確認できなければならない（MUST）。無効化や再設定コードの発行の対象を確かめるため。
- **FR-046**: 招待コードの発行画面と発行の操作は、有効な管理者だけが使えなければならない（MUST）。管理者でないユーザーには画面を表示せず、ログインしていない訪問者はログイン画面に移動させる（MUST）。画面を通さずに API に発行の操作を直接送っても、管理者でなければ発行してはならない（MUST NOT）。発行画面への入口は、管理者にだけヘッダーの操作の領域に表示する（MUST）。

#### 既存の設定との関係

- **FR-047**: ブラウザから API に直接つなぐ場面がなくなるため、API の CORS の許可（`CORS_ALLOWED_ORIGINS` と GitHub 変数 `CLOUD_RUN_CORS_ALLOWED_ORIGINS`）は、ローカル・CI・本番のすべてで外さなければならない（MUST）。API は他のオリジンからのブラウザのリクエストを許可する応答を返さない（MUST NOT）。設定の読み込み・デプロイの設定・手順書（`infra/`）・`.env.example` からも取り除く（MUST）。
- **FR-048**: ブラウザ向けの API の URL の環境変数（`NEXT_PUBLIC_API_URL`）は、中継先を表すサーバー側の環境変数に置き換え、手順書（`infra/vercel.md`）と `.env.example` と CI の設定もそろえなければならない（MUST）。

### Key Entities

- **ユーザー**: アプリを使う人。ログイン ID（一意、大文字と小文字を区別しない、本人だけに見せる、変更不可）、表示名（公開、変更可、重複可）、パスワードのハッシュ、管理者かどうか、有効か無効か、作成日時を持つ。後の機能で、キャラクターシートの所有者になる。
- **セッション**: ユーザーのログイン状態。セッション ID のハッシュ、ユーザー、作成日時、有効期限（最後に使った日時を含む場合がある）を持つ。ログアウト・パスワードの変更と再設定・ユーザーの無効化で削除される。
- **招待コード**: 登録を許可する、1 回だけ使えるコード。コードのハッシュ、発行した管理者、発行日時、有効期限、使った日時と登録されたユーザー（未使用なら空）を持つ。
- **再設定コード**: 特定のユーザーのパスワードを再設定するための、1 回だけ使えるコード。コードのハッシュ、対象のユーザー、発行日時、有効期限、使った日時（未使用なら空）を持つ。コマンドで発行するため、発行した管理者は記録しない。
- **ログインの失敗の記録**: ログイン ID（存在しないものを含む）ごとの、続けて失敗した回数、最後に失敗した日時、ロックが解ける日時。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 招待コードを受け取った人が、登録画面を開いてから 2 分以内に登録を終え、ログインした状態になれる。
- **SC-002**: 登録済みのユーザーが、ログイン画面を開いてから 30 秒以内にログインできる。
- **SC-003**: Chrome・Edge・Safari・Firefox の最新版とスマートフォンの標準ブラウザ（いずれも既定の設定）で、ログインした状態が再読み込みと画面の移動の後も 100% 保たれる。
- **SC-004**: ログアウト・パスワードの変更と再設定・ユーザーの無効化のあと、それ以前のログイン状態を使った操作は、次の 1 回目から 100% ログインしていない扱いになる。
- **SC-005**: 使用済み・期限切れ・存在しない招待コードと再設定コードは、100% 拒否される。同じコードを同時に 10 回使っても、成功は 1 回だけである。
- **SC-006**: 5 回続けて失敗したログイン ID は、ロックから 15 分が過ぎるまで、正しいパスワードでも 100% ログインできない。
- **SC-007**: 保存されたデータとログをすべて見ても、パスワード・招待コード・再設定コード・セッション ID の元の値は 1 件もわからない。
- **SC-008**: 他のユーザーやログインしていない訪問者が受け取る画面と API の応答に、他のユーザーのログイン ID が含まれることが 0 件である。
- **SC-009**: ログインしている状態でどの画面を開いても、最初の描画から表示名が表示され、ログインしていない表示が一瞬出ることがない。
- **SC-010**: 空の DB から、開発者が手順書だけを見て、10 分以内に最初の管理者を作ってログインできる。

## Assumptions

- この機能の利用者は、招待された小さなコミュニティの参加者と、その管理者である（ADR 0005、
  ADR 0006）。管理者は開発者を兼ねており、DB に接続してコマンドを実行できる。
- ADR 0006 の「後続の Spec で決めること」と CORS の扱いは、Clarifications のとおりに決めた。
  ADR 0006 には、この機能の実装の中で決定の内容を追記する。
- 管理者は、ユーザーの「管理者かどうか」の属性で表す。最初の管理者は、ADR 0005 の
  「移行する既存シートの所有者になるシステム管理者ユーザー」を兼ねてよい。
- 招待コードと再設定コードは、管理者がアプリの外（チャットなど）で相手に渡す。アプリから
  メールなどで送る機能は持たない。
- 招待コードは推測できない長さのランダムな値にするため、登録画面での招待コードの総当たりは
  現実的でないとみなし、登録画面の失敗の回数は数えない。
- 招待コードの一覧と取り消し、ユーザーの削除、ログイン ID の変更、管理者の権限の付け外し
  （コマンドで管理者を作る以外）は、この機能に含めない。必要になったら追加する。
- ログイン中の端末の一覧や、端末ごとのログアウトは、この機能に含めない。
- キャラクターシートの作成・更新と所有者の確認は、キャラクターシートの共通基盤の機能で扱う。
  所有者の移動（ADR 0005）も、この機能では扱わない。招待コードに既存シートを紐づけて、登録の
  ときに所有者を自動で移すかどうかは、データ移行の機能で改めて決める。この機能の招待コードには、
  シートに関する情報を持たせない。
- 本番環境の構築とデプロイは、この機能に含めない。ただし、手順書（`infra/`）と環境変数の例は、
  この機能の変更に合わせて更新する（FR-047、FR-048）。
- 登録・ログイン・アカウントの設定・再設定の画面は、UI 基盤（`001-ui-foundation`）の共通
  レイアウトと共通入力部品を使う。ヘッダーの右端の操作の領域は、UI 基盤で空けておいた場所を使う。
- ブラウザの対象は UI 基盤と同じく、最新の主要ブラウザ（Chrome、Edge、Safari、Firefox）と
  スマートフォンの標準ブラウザとする。ブラウザの Cookie が無効のときは、ログインできないことを
  表示すればよい。
