## Clarifications

### Session 2026-10-31

- Q: ヘッダーのテーマの切り替えで、利用者はどの選択肢から選べるようにするか？ → A: 旧システムと同じく、ボタン 1 つでライトとダークを切り替える（2 択）。切り替えるまでは端末の設定に合わせ、端末の設定に戻す手段は設けない。
- Q: フッターの著作権表記には、誰の名義を書くか？ → A: `© 2026 Qurioth`。
- Q: 数値入力で、画面側が何も指定しないときに受け付ける値はどれか？ → A: 0 以上の整数だけ。負の数と小数は、部品ごとに許可する。
- Q: web のテスト基盤には、本物のブラウザで画面を動かすテストも含めるか？ → A: 含めない。部品テスト（ブラウザを模した環境）だけにし、テーマのちらつき・画面幅・コントラストは目視で確かめる。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 共通レイアウトでトップページを見る (Priority: P1)

訪問者（ログインしていない人を含む）がトップページを開くと、全画面で共通のヘッダー・本文・
フッターの枠の中に、アプリの紹介と対応予定のゲームシステムの一覧が表示される。ヘッダーの
アプリ名からはいつでもトップページに戻れる。

**Why this priority**: 以降のすべての画面（認証、シートの一覧・編集）はこの枠の中に置かれる。
枠がないと、どの画面も作り始められない。

**Independent Test**: トップページを開き、ヘッダー・本文・フッターが表示されること、
アプリ名を押すとトップページに戻ること、スマートフォン幅でも崩れないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 訪問者がログインしていない, **When** トップページを開く, **Then** ヘッダー（アプリ名とテーマ切り替え）、アプリの紹介、ゲームシステムの一覧、フッターが表示される
2. **Given** トップページ以外の画面を開いている, **When** ヘッダーのアプリ名を押す, **Then** トップページに移動する
3. **Given** 幅 360px の画面で開いている, **When** トップページを表示する, **Then** 横スクロールが発生せず、ヘッダーの要素が重ならない
4. **Given** 本文が短い画面を開いている, **When** 画面を表示する, **Then** フッターは画面の下端に表示され、本文の途中に浮かない
5. **Given** ゲームシステムの一覧が表示されている, **When** まだシートを作れないシステムを見る, **Then** そのシステムは「準備中」と表示され、押しても存在しない画面には移動しない

---

### User Story 2 - ライト/ダークモードを切り替える (Priority: P1)

訪問者は、ヘッダーのボタン 1 つで、表示テーマをライトとダークの間で切り替えられる。
切り替えたテーマは同じブラウザで次に開いたときも使われる。まだ切り替えていない人には、
端末の設定に合わせたテーマで表示する。

**Why this priority**: 旧システムにある機能で、利用者が日常的に使っている。また、すべての
部品の色をテーマに対応させる必要があるため、部品を作り始める前に土台として決めておく。

**Independent Test**: テーマを切り替え、画面全体の色が変わること、再読み込み後も選択が
保たれること、読み込み時に別のテーマが一瞬表示されないことを確かめる。

**Acceptance Scenarios**:

1. **Given** テーマを一度も切り替えていない訪問者の端末がダーク設定, **When** トップページを開く, **Then** ダークテーマで表示される
2. **Given** ライトテーマで表示している, **When** ヘッダーのテーマ切り替えボタンを押す, **Then** 画面を再読み込みせずに、ヘッダー・本文・フッター・入力部品のすべてがダークテーマに変わる
3. **Given** ダークに切り替えた, **When** ページを再読み込みする・ブラウザを閉じて再び開く, **Then** 最初の描画からダークテーマで表示され、ライトテーマが一瞬表示されることはない
4. **Given** テーマを一度も切り替えていない, **When** ページを開いたまま端末の設定をライトからダークに変える, **Then** 画面もダークテーマに変わる
5. **Given** 一度テーマを切り替えた, **When** 端末の設定を変える, **Then** 画面のテーマは変わらず、利用者が切り替えたテーマのままになる
6. **Given** テーマ切り替えボタン, **When** キーボードだけで操作する, **Then** フォーカスして Enter・Space で切り替えができ、押すと何のテーマに切り替わるかが読み上げソフトにも伝わる

---

### User Story 3 - 共通の入力部品でフォームを組む (Priority: P2)

開発者は、シート画面や認証画面を作るときに、テキスト・数値・セレクト・テキストエリアの
共通入力部品を使う。どの部品もラベル・補足説明・エラー表示の形がそろっており、ライト・
ダークの両テーマとキーボード操作に対応している。利用者は、どの画面でも同じ見た目と操作で
入力できる。

**Why this priority**: 認証とシートの機能はどれも入力部品を大量に使う。先に形をそろえて
おかないと、画面ごとに見た目と操作がばらつく。ただし、トップページの表示とテーマ（P1）が
なくても作れるため P2 とする。

**Independent Test**: 部品の確認ページ（開発時のみ表示）で 4 種類の部品を表示・操作し、
自動テストで表示と操作を検証する。

**Acceptance Scenarios**:

1. **Given** ラベル付きのテキスト入力, **When** ラベルを押す, **Then** 入力欄にフォーカスが移り、読み上げソフトはラベルを入力欄の名前として読む
2. **Given** 数値入力, **When** 数字以外の文字を入力・貼り付けする, **Then** 値として受け付けず、直前の有効な値（または空）のままになる
3. **Given** 最小値・最大値を設定した数値入力, **When** 範囲外の値を入力して入力欄を離れる, **Then** 範囲外であることがエラーとして表示される
4. **Given** 数値入力, **When** 入力欄を空にする, **Then** 0 ではなく「未入力」として扱われる
5. **Given** セレクト, **When** キーボードで開いて上下キーと Enter で選ぶ, **Then** 選んだ項目が値になり、フォーカスはセレクトに戻る
6. **Given** テキストエリア, **When** 複数行の文章を入力する, **Then** 改行がそのまま保たれる
7. **Given** エラーのある入力部品, **When** 表示する, **Then** エラーの文言が入力欄の近くに表示され、色だけに頼らずエラーだとわかり、読み上げソフトにも伝わる
8. **Given** 無効（操作不可）にした入力部品, **When** 操作しようとする, **Then** 値は変わらず、無効であることが見た目でわかる
9. **Given** どの入力部品も, **When** ライト・ダークのどちらのテーマで表示しても, **Then** 文字・枠線・フォーカスの表示が背景と区別できる

---

### User Story 4 - ゲームシステムごとのフォントで表示する (Priority: P3)

シート画面の作り手（開発者）は、画面の一部を「このゲームシステムの領域」として指定するだけで、
そのシステム用のフォント（見出し用・特定の項目用など）を使える。利用者は、システムごとの
雰囲気に合った文字でシートを見られる。システムに属さない部分は、アプリ共通のフォントで表示する。

**Why this priority**: ゆうやけこやけやビギニングアイドルのシート（後の機能）で必要になるが、
シート画面がまだないため、この機能では仕組みと確認だけを用意する。

**Independent Test**: 部品の確認ページで、システムを指定した領域とそうでない領域を並べ、
フォントが切り替わることを目視で確かめる。システムの指定が領域に反映されることは自動テストで確かめる。

**Acceptance Scenarios**:

1. **Given** ゆうやけこやけの領域, **When** 見出しを表示する, **Then** ゆうやけこやけ用の見出しフォントで表示される
2. **Given** ゆうやけこやけの領域の中で「筆文字」の役割を指定した要素, **When** 表示する, **Then** ゆうやけこやけ用の筆文字フォントで表示される
3. **Given** システムを指定していない領域, **When** 表示する, **Then** アプリ共通のフォントで表示される
4. **Given** システム用フォントの読み込みが遅い・失敗した, **When** 表示する, **Then** 文字は代替フォントですぐに表示され、読めない時間がない

---

### User Story 5 - web の自動テストを実行する (Priority: P2)

開発者は、web の自動テストを手元と CI で実行できる。テストは部品単位で、ブラウザを模した
環境で部品の表示と、クリック・キーボードによる操作を検証する。本物のブラウザで画面を動かす
テストは、この機能では用意しない。

**Why this priority**: この機能で作る入力部品とテーマ切り替えの検証に必要。以降の機能でも
テストを書く前提になる。トップページの表示（P1）とは独立して用意できる。

**Independent Test**: API と DB を起動していない状態で web のテストを実行し、成功すること、
わざと壊したテストが失敗として報告されることを確かめる。

**Acceptance Scenarios**:

1. **Given** 依存パッケージを入れた直後の手元の環境, **When** 既存のテスト実行コマンドを実行する, **Then** Go のテストと一緒に web のテストも実行される
2. **Given** API と DB を起動していない, **When** web のテストを実行する, **Then** web のテストは成功する
3. **Given** web のテストが 1 件失敗する変更, **When** CI が実行される, **Then** CI が失敗し、失敗したテスト名がわかる
4. **Given** 入力部品のテスト, **When** キーボード操作を模したテストを書く, **Then** 実際の利用者の操作に近い形で検証できる

---

### Edge Cases

- ブラウザの保存領域が使えない（プライベートブラウズで制限されているなど）ときは、テーマの
  選択を保存できない。この場合も切り替え自体はその画面で働き、次に開いたときは端末の設定に
  合わせる。エラーは表示しない。
- JavaScript が無効なときは、テーマの切り替えはできないが、端末の設定に合わせたテーマで
  ページは読める。
- 保存されているテーマの値が不正（手で書き換えられたなど）なときは、端末の設定に合わせる。
- アプリ名が長い・画面が狭いときは、ヘッダーの要素を折り返さずに収め、テーマ切り替えは
  常に押せる位置に残す。
- 数値入力に全角数字（「１２」など）が入力されたときは、半角の数値として受け付ける。
- 数値入力に小数・負の数が入力されたときの扱いは、部品ごとに許可するかどうかを指定できる。
  指定がない場合は 0 以上の整数だけを受け付け、負の数・小数はエラーとして表示する。
- セレクトの選択肢が多い（数十件）ときは、一覧が画面からはみ出さずにスクロールできる。
- セレクトの選択肢の文言が長いときは、選択後の表示が入力欄の幅を超えず、省略して表示する。
- システム用フォントに含まれない文字（記号・旧字体など）は、代替フォントで表示され、
  文字が欠けない。

## Requirements *(mandatory)*

### Functional Requirements

#### 共通レイアウト

- **FR-001**: すべての画面は、共通のヘッダー・本文・フッターの枠の中に表示されなければならない（MUST）。
- **FR-002**: ヘッダーには、トップページへ移動できるアプリ名と、テーマの切り替えを表示しなければならない（MUST）。後の機能でログイン状態やメニューを追加できる場所を空けておく。
- **FR-003**: フッターには、アプリ名と著作権表記 `© 2026 Qurioth` を表示しなければならない（MUST）。
- **FR-004**: 本文が短い画面でも、フッターは画面の下端に表示しなければならない（MUST）。
- **FR-005**: 共通レイアウトは、幅 360px 以上の画面で横スクロールを発生させてはならない（MUST）。
- **FR-006**: キーボードの利用者が、ヘッダーを飛ばして本文へ移動できる手段を用意しなければならない（MUST）。
- **FR-007**: 画面の文書の言語を日本語として示し、各画面にアプリ名を含むタイトルを付けなければならない（MUST）。

#### トップページ

- **FR-008**: トップページには、アプリの紹介文と、対応予定のゲームシステム（ゆうやけこやけ、ビギニングアイドル）の一覧を表示しなければならない（MUST）。
- **FR-009**: シート画面がまだないゲームシステムは「準備中」と表示し、存在しない画面へのリンクにしてはならない（MUST）。
- **FR-010**: トップページは、ログインせずに閲覧できなければならない（MUST）。また、API が止まっていても表示できなければならない（MUST）。

#### テーマ

- **FR-011**: 利用者は、ヘッダーのボタン 1 つで、表示テーマをライトとダークの間で切り替えられなければならない（MUST）。「端末の設定に合わせる」に戻す手段は設けない。
- **FR-012**: 切り替えたテーマは同じブラウザに保存し、次に開いたときに使わなければならない（MUST）。テーマの選択をサーバーに送ってはならない（MUST NOT）。
- **FR-013**: テーマを一度も切り替えていない利用者には、端末の設定に合わせたテーマで表示しなければならない（MUST）。
- **FR-014**: ページの最初の描画から使うべきテーマで表示し、別のテーマが一瞬表示されてはならない（MUST NOT）。
- **FR-015**: テーマを一度も切り替えていない利用者には、ページを開いたまま端末の設定が変わったら、表示も追従しなければならない（MUST）。一度切り替えた利用者には、端末の設定の変化を反映してはならない（MUST NOT）。
- **FR-016**: すべての共通部品（ヘッダー、フッター、入力部品）は、両方のテーマで本文の文字と背景のコントラスト比 4.5:1 以上を満たさなければならない（MUST）。
- **FR-017**: 色はテーマごとに名前の付いた色（背景、文字、枠線、強調、エラーなど）として定義し、部品はその名前を使わなければならない（MUST）。後の機能でゲームシステムごとに色を変えられるようにするため。

#### フォント

- **FR-018**: アプリ共通のフォントは、日本語の本文を読みやすく表示できるものでなければならない（MUST）。
- **FR-019**: 画面の一部をゲームシステムの領域として指定すると、その領域ではそのシステム用のフォントを使えなければならない（MUST）。
- **FR-020**: この機能では、ゆうやけこやけ（見出し用・筆文字用）とビギニングアイドル（見出し用）のフォントを用意しなければならない（MUST）。
- **FR-021**: システム用フォントの読み込みが終わるまで、または失敗したときは、代替フォントで文字を表示しなければならない（MUST）。フォントの切り替わりで、配置が大きくずれてはならない（SHOULD NOT）。
- **FR-022**: システム用フォントは、そのシステムの領域を表示しない画面の表示を遅くしてはならない（SHOULD NOT）。

#### 共通入力部品

- **FR-023**: テキスト入力・数値入力・セレクト・テキストエリアの 4 種類の共通入力部品を用意しなければならない（MUST）。
- **FR-024**: 4 種類の部品は、ラベル・補足説明・エラー文言・必須の表示・無効状態を、同じ指定方法と同じ見た目で持たなければならない（MUST）。
- **FR-025**: ラベル・補足説明・エラー文言は、支援技術で入力欄と関連付けて読み上げられなければならない（MUST）。
- **FR-026**: 4 種類の部品はすべて、キーボードだけで操作でき、フォーカスの位置が目で見てわからなければならない（MUST）。
- **FR-027**: 数値入力は、数値以外を値として受け付けてはならない（MUST NOT）。全角数字は半角の数値として受け付ける。空欄は 0 ではなく「未入力」として扱う（MUST）。
- **FR-028**: 数値入力には、最小値・最大値、負の数を許可するか、小数を許可するか、を指定できなければならない（MUST）。指定がない場合は 0 以上の整数だけを受け付ける（MUST）。範囲外の値と、許可していない負の数・小数はエラーとして表示する（MUST）。
- **FR-029**: セレクトは、選択肢が多いときにスクロールでき、未選択の状態（プレースホルダー）を表示できなければならない（MUST）。
- **FR-030**: テキストエリアは、複数行の入力で改行を保たなければならない（MUST）。
- **FR-031**: 入力部品は、ゲームシステムの領域の中に置いたときに、その領域の形（大きな文字、表のマス目など）に合わせて、大きさと見た目を画面側から変えられなければならない（MUST）。部品の内部構造に依存した上書きをしなくても変えられるようにする。
- **FR-032**: 開発時だけ表示される部品の確認ページを用意し、4 種類の入力部品の各状態（通常、エラー、無効、必須）と、システムごとのフォントを両方のテーマで確認できるようにしなければならない（MUST）。本番の環境では、このページを公開してはならない（MUST NOT）。

#### テスト基盤

- **FR-033**: web の自動テストを、既存のテスト実行の入口から Go のテストと一緒に実行できなければならない（MUST）。web だけを実行する手段も用意する（SHOULD）。
- **FR-034**: web の自動テストは、API と DB を起動しなくても実行できなければならない（MUST）。
- **FR-035**: web の自動テストは、CI で実行し、失敗したら CI を失敗させなければならない（MUST）。
- **FR-036**: テストでは、部品の表示内容と、クリック・キーボード入力による操作を、ブラウザを模した環境で、利用者の操作に近い形で検証できなければならない（MUST）。本物のブラウザで画面を動かすテストは、この機能では用意しない。
- **FR-037**: この機能で作る入力部品・テーマ切り替え・共通レイアウトには、受け入れシナリオに対応する自動テストを用意しなければならない（MUST）。ただし、ブラウザを模した環境で確かめられない項目（最初の描画のテーマ、画面幅ごとの配置、色のコントラスト、フォントの見た目）は、部品の確認ページとトップページを本物のブラウザで開いて目視で確かめる。

### Key Entities

- **テーマの選択**: 利用者がブラウザごとに切り替えた表示テーマ。値は「ライト」「ダーク」のいずれかで、一度も切り替えていなければ値を持たない（端末の設定に合わせる）。ブラウザにだけ保存し、サーバーには持たない。
- **ゲームシステム**: シートの対象となる TRPG のシステム。識別子、表示名、紹介文、対応状況（利用可能 / 準備中）、使うフォントの組（役割ごと: 見出し、筆文字など）を持つ。この機能では画面の表示用の定義だけを持ち、DB には保存しない。
- **入力部品の共通属性**: ラベル、補足説明、エラー文言、必須、無効。4 種類の部品が共通して持つ。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 幅 360px から 1920px までのどの画面幅でも、トップページで横スクロールが発生せず、ヘッダー・本文・フッターがすべて表示される。
- **SC-002**: テーマを切り替えたあと、再読み込み・ブラウザの再起動をしても、10 回中 10 回とも最初の描画から切り替えたテーマで表示される。
- **SC-003**: 4 種類の入力部品とテーマ切り替えを、マウスを使わずに操作して値の入力・選択を完了できる。
- **SC-004**: 共通部品の本文の文字は、ライト・ダークの両方のテーマでコントラスト比 4.5:1 以上を満たす。
- **SC-005**: 部品テストでのアクセシビリティの自動チェックで、共通レイアウトと 4 種類の入力部品に重大な違反が 0 件である（色のコントラストは SC-004 で目視とツールで確かめる）。
- **SC-006**: 一般的なモバイル回線相当の条件で、トップページの主な内容が 2.5 秒以内に表示される。
- **SC-007**: システム用フォントが読み込めない状態でも、文字が読めない時間が生じない。
- **SC-008**: API と DB を起動していない状態で、web の自動テストが 1 分以内にすべて成功する。

## Assumptions

- この機能の利用者は、ログインしていない訪問者と、後の機能を作る開発者である。ログインや
  ユーザーメニューは「認証」の機能で追加する。
- 技術の選択は、constitution と ADR 0004 の方針（スタイルとレイアウトは Tailwind CSS、操作の
  伴う部品は shadcn/ui、MUI は使わない、フォントは Next.js のフォント読み込みを使う）に従う。
  ADR 0004 で「UI 基盤の Spec で決める」とした次の事項は、`/speckit-clarify` と `/speckit-plan`
  で決める: Tailwind CSS と shadcn/ui のバージョン、shadcn/ui の土台（Radix UI か Base UI か）、
  共通入力部品の形、フォームのライブラリ、テーマの色の定義とダークモードの切り替え方。
- テーマの切り替えは、旧システムと同じボタン 1 つの 2 択（ライト / ダーク）にする。一度切り替えた
  利用者は端末の設定に合わせる状態に戻れないが、旧システムの操作を変えないことを優先する。
- システム用のフォントは、旧システムと ADR 0004 に合わせ、ゆうやけこやけは見出しに
  Mochiy Pop P One、筆文字に Yuji Syuku、ビギニングアイドルは見出しに Mochiy Pop P One を使う。
  ADR 0004 の「Mochiy Pop One」は、旧システムで使っていた Mochiy Pop P One のことと解釈する。
  ほかのシステム（キルデスビジネスなど）のフォントは、そのシステムのシートの機能で追加する。
- トップページの対応予定システムは、README の「Spec Kit で進める予定の機能」にある
  ゆうやけこやけとビギニングアイドルの 2 つとする。旧システムのトップページにあった
  工事中のシステム（キルデスビジネス、アマデウス、パラノイア）は載せない。
- 現在のトップページにある API の接続状態の表示は、利用者向けの情報ではないため、トップ
  ページから外し、部品の確認ページ（開発時のみ）に移す。
- 部品の確認ページは開発時の確認用であり、デザインシステムの文書化（Storybook のような
  カタログ）は範囲外とする。
- 本物のブラウザで画面を動かすテスト（E2E テスト）は、画面をまたぐ操作（ログイン、シートの
  作成と保存など）が増えて必要になった機能で導入を検討する。
- ブラウザの対象は、最新の主要ブラウザ（Chrome、Edge、Safari、Firefox）とスマートフォンの
  標準ブラウザとする。
- 入力値の保存（API への送信）とフォーム全体の検証は、シートと認証の機能で扱う。この機能の
  入力部品は、値の表示・入力・部品単位のエラー表示までを担う。
- ダイアログ、トースト、タブ、チェックボックスなど、4 種類以外の部品は、必要になった機能で
  追加する。
